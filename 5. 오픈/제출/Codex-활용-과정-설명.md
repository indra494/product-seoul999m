# Codex와 함께 게임을 만든 과정

## 제출 폼용 상세본

이 프로젝트는 처음부터 완성된 게임 아이디어를 Codex에 입력해 한 번에 생성한 결과물이 아닙니다. 시작 단계에서 저는 먼저 “Codex가 실제로 어느 정도 수준의 게임까지 만들 수 있을까?”를 확인하고 싶었습니다. 생각나는 여러 게임 아이디어를 작은 테스트 케이스와 프로토타입으로 만들어 보면서 구현 속도, 브라우저에서의 조작 가능성, 콘텐츠 제작량과 남은 기간을 비교했습니다. 그 과정에서 단기간 안에 완성하기 어렵거나 핵심 재미를 증명하기 힘든 아이디어는 제가 직접 제외했습니다. 여러 가능성을 실험한 뒤, 짧은 시간에도 `직접 땅을 파서 길을 만들고 그 길로 부대를 보낸다`는 차별점을 명확하게 보여줄 수 있다고 판단해 `서울 지하 999M`을 최종 프로젝트로 선택했습니다.

게임의 큰 그림은 제가 기획했습니다. 오염된 지상을 피해 지하 999m에 도시를 세운 세계관, 휴먼·버그본·AI 로봇의 세 종족, 각 캐릭터의 성격과 관계, 캠페인 스토리, 직접 굴착과 자동 진군대가 결합된 전투 규칙을 먼저 정했습니다. 상대의 길이 보이지 않는 준비 단계, 개전 후 부대가 직접 만든 터널을 따라 이동하는 구조, 거점 코어를 파괴하는 승리 조건처럼 게임의 전체 전략과 핵심 룰도 제가 결정했습니다. Codex와는 이 원안을 기준으로 계속 대화하며 규칙을 구체화하고, 실제 플레이에서 재미가 약하거나 복잡한 부분을 다시 줄이고 맞추는 방식으로 협업했습니다.

### 1. Codex를 사용하기 위한 작업 구조 설계

저는 Codex를 단순한 코드 생성 도구가 아니라 장기간 함께 작업하는 개발 파트너로 사용하기 위해, 코드를 만들기 전에 작업 방식부터 설계했습니다. 전체 프로젝트를 `아이디어·정보 → 기획 → 설계 → 개발 → 오픈`의 다섯 단계로 나눴습니다.

- `1. 정보`에는 해커톤 일정, 제출 조건과 외부 조사 자료를 보관했습니다.
- `2. 기획`에는 게임의 목표와 재미, 세계관, 종족과 캐릭터, 맵, 유닛, 전투 규칙과 캠페인을 기록했습니다.
- `3. 설계`에는 프로토타입 구조, 전투 런타임, AI와 네트워크, 이동·충돌 복구, 콘텐츠 모듈과 배포 방식을 문서화했습니다.
- `4. 개발`에는 실제 게임 코드, 에셋, 자동 테스트와 빌드 설정을 두었습니다.
- `5. 오픈`에는 공개 링크, 200자 소개, 플레이 방법, 썸네일, 영상과 최종 제출 자료를 관리했습니다.

또한 `99. codex` 폴더를 별도로 만들고 Codex의 작업 규칙을 정했습니다. `project-memory.md`에는 장기적으로 유지해야 할 결정과 폐기한 방향을, `current-session.md`에는 현재 상태와 바로 다음 작업을 기록했습니다. 정보 조사, 기획, 설계, 개발, 테스트, 문서화, 공개 작업마다 별도의 지침 파일을 만들었고 기획·설계 템플릿과 전체 작업 로그도 유지했습니다. 플레이 규칙이 바뀌면 기획서를 먼저 수정하고, 기술 구조가 바뀌면 설계를 갱신한 뒤 코드를 변경하며, 구현 후에는 테스트와 프로덕션 빌드를 실행하도록 순서를 고정했습니다. 이 구조를 통해 긴 작업에서도 Codex가 이전 결정을 잊거나 폐기한 아이디어를 다시 구현하는 문제를 줄였습니다.

### 2. 아이디어·기획·디자인 단계

캐릭터 디자인, 맵 디자인과 유닛 디자인도 함께 진행했습니다. 저는 각 종족이 어떤 인상을 주어야 하는지, 캐릭터가 이야기에서 어떤 역할을 맡는지, 전투에서 어떤 방식으로 구분되어야 하는지 큰 방향을 정했습니다. Codex는 이를 캐릭터별 기술, 사거리, 역할, 애니메이션과 데이터 구조로 구체화하고, 캐릭터끼리 기술이 중복되거나 특정 역할이 비어 있는지 검토했습니다. 맵 역시 제가 원하는 지하 서울의 분위기와 플레이 흐름을 기준으로, Codex와 함께 거점 구조, 흙벽, 광맥, 공동구역, 비밀 굴착전과 개방 전선전의 차이를 구체적인 규칙으로 만들었습니다.

도트 그래픽은 의도적인 선택이었습니다. 저는 전문 그래픽 작업에 자신이 없었고, 제한된 기간 안에 많은 캐릭터와 유닛을 일관된 스타일로 만들어야 했습니다. 동시에 서울의 지하 시설, 고철 장비와 서로 맞지 않는 물건을 조합한 B급 감성을 살리고 싶었습니다. 그래서 사실적인 고해상도 그래픽보다 작은 캐릭터도 역할이 구분되고 과장된 연출이 어울리는 도트 분위기를 선택했습니다. 저는 미술 방향과 B급 감성의 기준을 정하고 결과물을 비교·선택했으며, Codex는 캐릭터·거점·유닛의 이미지 프롬프트와 제작 규격을 정리하고 게임 안에서 일관되게 보이도록 에셋과 화면을 조정했습니다.

### 3. 설계·개발 단계에서의 Codex 활용

기획이 정리된 뒤 Codex는 React·TypeScript 기반의 실제 게임 코드, 데이터 구조, 전투 로직과 테스트를 구현했습니다. 직접 굴착, 안개와 탐사 시야, 상대 굴착이 보이지 않는 30초 준비 단계, 자동 진군대, A/B 공격 경로와 다음 WAVE 병력 배분, 종족별 영웅·시설·전술지원·아이템, 캠페인, 컴퓨터 대전과 방 코드 온라인 1:1을 단계적으로 개발했습니다. 저는 각 단계마다 게임을 직접 플레이하면서 속도, 조작감, 정보량과 난이도를 판단하고 수정 방향을 결정했습니다.

예를 들어 온라인 참가자가 판 땅굴이 다시 벽으로 돌아가는 문제는 Codex가 방장과 참가자 두 브라우저를 동시에 실행해 재현하고, 양쪽의 지형 권한이 일치하지 않는 것이 원인임을 찾았습니다. 이후 굴착 명령, 클라이언트 순번, 방장 승인, 승인 전 예측과 실패 복구를 구현했습니다. 전투 입력마다 전체 방 상태를 저장·전송해 끊기던 문제도 작은 명령과 최신 스냅샷만 주고받는 구조로 변경했습니다.

AI 영웅이 길을 찾지 못하고 멈추는 문제에는 이동 정체를 감지해 공격 경로를 다시 계산하는 복구 로직을 추가했습니다. 미니맵의 그림과 입력 영역이 어긋나는 문제는 캔버스와 CSS 좌표를 통일해 해결했고, 모바일에서는 하단 조작부가 전장을 가리는 문제를 왼쪽 조작 레일 구조로 다시 설계했습니다. 이런 문제는 Codex가 원인을 분석하고 수정안을 구현했지만, 문제가 실제로 해결되었는지와 플레이 감각이 좋아졌는지는 제가 직접 PC와 모바일에서 확인하고 승인했습니다.

개발 과정에서 Codex는 문제 가능성을 꾸준히 관리했습니다. 기획과 구현의 불일치, 캐릭터 기술 중복, 모바일 화면 넘침, 네트워크 권한 충돌, AI 정체, 브라우저 단축키 충돌과 회귀 오류를 문서와 테스트로 추적했습니다. 기능을 변경할 때마다 관련 문서를 함께 갱신했고, 프로덕션 빌드, 자동 회귀 테스트, ESLint와 실제 브라우저 플레이를 반복했습니다. 최종 게임은 프로덕션 빌드를 포함한 98개 회귀 테스트를 통과했고 ESLint 오류는 0건이었습니다.

### 4. 오픈과 제출 단계

공개 단계에서도 Codex를 활용했습니다. 실제 게임에 없는 기능을 소개문에 잘못 넣지 않도록 코드와 200자 소개를 대조했고, 게임 안에 빠른 시작과 상세 교본을 만들었습니다. 여러 썸네일 구도를 만든 뒤 작은 크기로 축소해 제목과 핵심 플레이가 읽히는지 비교했으며, 약 29분의 원본 플레이 영상 7개를 분석해 2분 56초 소개 영상으로 편집했습니다. 모바일에서 영상 음성이 나오지 않는 문제도 MP4 내부 오디오 코덱이 Opus인 것을 확인하고 AAC-LC로 변환해 해결했습니다.

### 5. 개발자와 Codex의 역할 구분

이 프로젝트에서 저는 단순히 아이디어를 입력한 사람이 아니라 프로젝트의 방향을 결정하고 Codex를 운용한 기획자이자 개발 책임자 역할을 했습니다. 어떤 아이디어를 시험하고 버릴지, 게임의 핵심 재미와 세계관, 전략과 룰, 캐릭터성, 스토리, 맵·유닛·미술 방향, 조작감, 난이도와 기능 우선순위를 제가 결정했습니다. 실제 게임을 계속 플레이하며 `굴착이 느리다`, `온라인이 끊긴다`, `버튼이 보이지 않는다`, `영상 초반이 루즈하다`와 같은 문제를 찾아 피드백했고, Codex의 제안을 채택하거나 폐기하는 최종 판단도 제가 내렸습니다. 원본 영상 녹화, 공개 도메인과 배포 계정 관리, 외부 기기 확인과 최종 제출 결정 역시 제가 직접 진행했습니다.

Codex는 제가 정한 방향을 실제 결과물로 빠르게 구현하는 역할을 맡았습니다. 코드 작성과 수정, 원인 분석, 테스트 자동화, 기획·설계 문서의 정합성 관리, 에셋 제작 지원과 제출 자료 편집을 담당했습니다. 즉, 개발자가 게임의 목표와 재미를 설계하고 품질을 판단했으며, Codex는 그 판단을 구현하고 검증하는 개발 파트너였습니다. 처음부터 Codex가 일할 구조를 설계하고, 단계별 문서와 메모리, 테스트를 통해 지속적으로 관리했기 때문에 짧은 기간에도 큰 아이디어를 실제로 플레이 가능한 웹게임으로 완성할 수 있었습니다.

## 축약본

처음에는 “Codex가 어느 수준의 게임까지 만들 수 있을까?”를 확인하기 위해 여러 아이디어를 작은 테스트 게임으로 구현했습니다. 저는 기간 안에 완성하기 어려운 아이디어를 제외하고, 직접 땅굴을 파서 공격로를 만들고 부대를 보내는 `서울 지하 999M`을 선택했습니다. 세계관, 세 종족, 캐릭터성과 스토리, 핵심 전략과 룰, 맵·유닛·도트 그래픽의 B급 미술 방향은 제가 기획했습니다.

Codex를 체계적으로 활용하기 위해 프로젝트를 정보·기획·설계·개발·오픈의 다섯 단계로 나누고, 장기 메모리·현재 작업·단계별 지침·템플릿·작업 로그를 별도로 운영했습니다. Codex는 이 구조 안에서 직접 굴착, 30초 준비 단계, 자동 진군대, A/B 경로, 캠페인·AI 대전·온라인 1:1을 구현하고 온라인 권한 충돌, AI 정체, 미니맵 좌표, 모바일 HUD 문제를 해결했습니다. 최종 게임은 프로덕션 빌드 포함 98개 회귀 테스트와 ESLint 오류 0건을 확인했습니다.

저는 매 단계에서 PC와 모바일로 직접 플레이하며 조작감, 난이도, 기능 우선순위와 결과물의 채택 여부를 결정했고, 영상 녹화·배포·최종 제출을 담당했습니다. Codex는 코드·분석·테스트·문서화를 맡고, 개발자는 게임의 목표와 재미를 설계하고 최종 품질을 판단하는 방식으로 협업했습니다.
